### Ключевые технические решения

**1. Денежные суммы**

Предлагаю хранить суммы как десятичные строки, а вычисления выполнять через `decimal.js`. Обычный `Number` не использовать для денежных расчётов.

После изучения API фиксируем:

- допустимую точность каждого актива;
- минимальную и максимальную сумму;
- включается ли комиссия в введённую сумму или добавляется сверху;
- порядок и способ округления;
- правила вычисления USD total.

Ввод суммы должен сохраняться строкой: незавершённые значения вроде `0.` допустимы во время редактирования, но не при отправке.

**2. Баланс после отправки Claim — два подхода**

| Подход | Преимущества | Недостатки |
|---|---|---|
| Сразу уменьшить баланс оптимистически | Пользователь сразу видит изменение | При отказе баланс придётся вернуть; возможны скачки и двойное вычитание при обновлении |
| Показывать подтверждённый сервером баланс и отдельно pending Claim | Нет выдуманного окончательного списания; состояние операции понятно | Нужно явно объяснить, что сумма ещё обрабатывается |

**Предлагаю второй подход.** Сразу показываем операцию «Обрабатывается» с суммой и блокируем её повторную отправку. Баланс обновляем по серверным данным. Если API различает available и pending, отображаем эти значения напрямую. Локально второй раз сумму не вычитаем.

Так пользователь получает мгновенную обратную связь, а баланс остаётся согласован с сервером.

**3. Таймаут при отправке Claim**

Таймаут означает **неизвестный результат**, а не отказ.

- Сохраняем идентификатор попытки до отправки.
- Если API поддерживает idempotency key, используем один ключ для одной операции.
- При таймауте показываем «Проверяем статус операции».
- Проверяем результат предусмотренным API способом.
- Повторяем отправку только с гарантией отсутствия дубля.
- Если такой гарантии API не предоставляет, не делаем автоматический повтор и явно описываем ограничение.

Автоматические повторы mutation в TanStack Query для Claim отключаем.

### Денежная логика

API принимает суммы только строками:

- Допустимы: `"0.5"`, `"12"`.
- Недопустимы: `".5"`, `"1."`, `"05"`, `"1e-3"`.
- Точность задаётся полем `decimals` каждого актива.
- Ограничения: `minAmount ≤ amount ≤ available`.
- Комиссия фиксированная для актива и **вычитается из суммы**: `receiveAmount = amount − fee`.
- **Max = available** — дополнительно вычитать комиссию не нужно.

Для расчётов оставляем `decimal.js`. После создания Claim показываем `fee` и `receiveAmount` из ответа сервера.

Проверка доступного баланса на сервере выполняется в реальном времени. Поэтому даже корректная по последнему snapshot сумма может быть отклонена — такую ошибку нужно показать и обновить данные.

### Баланс после Claim

Простого обновления запроса недостаточно: сервер может вернуть старый snapshot.

Предлагаю такой вариант:

1. Сразу показывать отдельную карточку Claim со статусом `pending`.
2. Подписывать баланс временем `asOf` и сообщением «Операция принята, баланс обновляется».
3. Для минимальной реализации блокировать новый Claim **этого актива**, пока операция и обновление snapshot не согласованы.
4. Не вычитать сумму локально из серверного баланса — это исключит двойное списание на экране.
5. Проверять статус Claim примерно каждые 3 секунды; после завершения обновлять балансы.

`pending` в балансе — ещё не подтверждённый cashback. `claiming` — средства в незавершённых Claim. Это разные состояния, их нужно подписать отдельно.

### Таймаут и повторная отправка

API предоставляет необходимую защиту: **`Idempotency-Key`**.

Перед отправкой сохраняем в браузере ключ и точное тело запроса. Если ответ потерян, произошёл сетевой сбой или получен `504`, повторяем **тот же запрос с тем же ключом**. Сервер вернёт исходный Claim и не создаст новый.

После получения `id` отслеживаем операцию через `GET /v1/claims/{id}`.

Важные детали:

- Нельзя генерировать новый ключ при повторе неизвестного результата.
- Нельзя менять сумму или destination у сохранённой попытки.
- Незавершённую попытку нужно восстанавливать после перезагрузки страницы.
- Попытки и кеш должны быть изолированы по токену.
- При `429` ждём `retryAfterMs`, не запускаем немедленные повторы.
- При `401` предлагаем заменить токен.
- При `409` останавливаем повтор: ключ использован с другим телом.

### Что меняется в плане

Приоритет реализации теперь такой:

1. **API-клиент и ввод токена** — единый base URL, обработка ошибок, смена токена с очисткой кеша.
2. **Home** — available, pending, claiming для каждого актива, USD total, `asOf`, loading/error/retry/refresh.
3. **Денежные функции и тесты** — формат, точность, min/max, комиссия, totals.
4. **Форма Claim** — загрузка `claim-options`, выбор destination, сумма, Max, подтверждение.
5. **Надёжная отправка** — сохранённый idempotency key, восстановление после таймаута и перезагрузки.
6. **Отслеживание Claim** — pending/completed/failed и согласование со snapshot баланса.
7. **Activity** — только после готовности основного сценария.

### Что нужно явно зафиксировать в NOTES.md

В документации остаются неоднозначности:

- **USD total:** предлагаю считать `(available + pending + claiming) × usdPrice` по всем активам и подписать, что включено.
- **Округление USD:** считать с полной точностью, округлять только итог для отображения до двух знаков.
